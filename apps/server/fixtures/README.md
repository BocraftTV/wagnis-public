# Phase-3 fixtures

`phase3-3p.json` and `phase3-2p.json` are real saved game states (the `rooms.state_json` column) written by the
**Phase-3 code**, taken from the SQLite database of a running server. They are the mandatory input of the
`stateVersion` migration test (plan 004, question 19): a Phase-3 state must load as `"domination"` and keep
accepting actions.

- Phase-3 commit: `60d73248267a5a7587e95aa47523e7ac59ea7f09` (`main` before any Phase-4 change; no `stateVersion`,
  no `victoryMode`, `secret.mission` is still `null`).
- Generated by `scripts/make-phase3-fixture.mjs` through the real path: production server (`apps/server/dist`) with a
  temporary `WAGNIS_DB_PATH`, rooms, joining, start and all actions over the real HTTP and WebSocket interfaces.
  Commands on that commit:

  ```
  npm ci
  npm run build
  node scripts/make-phase3-fixture.mjs
  ```

- `phase3-3p.json`: 3 players, turn 4, phase `attack`, after an attack with a conquest in the current turn, three
  turns before it each with a conquest (drawn cards in the hands).
- `phase3-2p.json`: 2 players, turn 3, phase `attack`, same shape (Phase 3 has no neutral owner).
- The content is the stored row unchanged, only pretty-printed (and formatted by Prettier).
- **Do not edit by hand** and do not regenerate with Phase-4 code: the point is that they come from the old code.
- They contain only player IDs and game data. No tokens, no create code, no names (names live in the `players`
  table, not in the state). This was checked by searching the files for `token`, `createCode` and `hash`.

# Phase-4 fixtures (plan 005, step 0)

`phase4-rooms.json` and `phase4-schema.sql` are the saved rows and the table definitions of a real database written
by the **Phase-4 code**. They are the mandatory input of the old-database tests of Phase 5 (`rooms.map_id`
migration, running rooms on `testland` stay playable, `stateVersion` stays 4).

- Phase-4 commit: `c90ac654a3eb806d29137687b155e94ed28e7e2f` (`main` before any Phase-5 change; no `rooms.map_id`,
  `schema_meta.version` is 1).
- Generated by `scripts/make-phase4-fixture.mjs` through the real path: production server (`apps/server/dist`) with a
  temporary `WAGNIS_DB_PATH`, rooms, joining, start and all actions over the real HTTP and WebSocket interfaces.
  Commands on that commit:

  ```
  npm ci
  npm run build
  node scripts/make-phase4-fixture.mjs
  ```

- `phase4-rooms.json`: `schemaMetaVersion` and three rooms, each with its `rooms` row and `players` rows:
  - `lobby`: 2 players (host and one more), not started, `state_json` is `null`.
  - `playing-3p`: 3 players on `testland`, turn 2, phase `attack`, after a completed turn with a conquest and a
    second conquest in the current turn (missions in the state, a drawn card in a hand).
  - `playing-2p-neutral`: 2 players plus neutral on `testland`, same shape.
- `state_json` is the stored text parsed and pretty-printed (the script checks that `JSON.stringify` of it gives the
  stored text back; a test inserts it with `JSON.stringify`). The other columns are unchanged.
- `phase4-schema.sql`: the `CREATE` statements exactly as SQLite stored them (from `sqlite_master`). The `Store`
  inserts the row `schema_meta (version) = 1` after creating them.
- Token hashes are replaced by placeholders (`PLACEHOLDER-TOKEN-HASH-<room>-<seat>`). The original tokens never
  left the temporary database, which is deleted. Player names (Anna, Ben, Cleo) and room IDs are random test data.
- **Do not edit by hand** and do not regenerate with Phase-5 code: the point is that they come from the old code.
- They contain no tokens and no create code. This was checked by searching the files for `token`, `createCode`,
  `secret` (only the game-state field `secret` occurs) and for long hex strings (none). The create code of the run
  is random, kept only in the script process and never written.
